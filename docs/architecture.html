Coverage Gap POC Map

The tool finds test cases that should exist in Zephyr Scale but don't. The new flow explores four sources in parallel (requirements, code, the running UI and the existing Zephyr tests), joins them into a single context, and designs tests only for what that context shows as uncovered or partial. Nothing is written to Zephyr until a tester approves it.

Target flow

Each box shows how much of today's code it can reuse. Each explorer writes its own file, and only the context builder combines them.

What breaks when the explorers run in parallel

Today's chain relies on its order in four places. Each needs a fix before the fan-out works.

Code reads requirement output

The code stage sends the story scenario titles to the LLM so it can skip duplicates (stages.mjs:276).

Drop the titles from extract-code and remove duplicates in the context builder.

All stages write state.json

Every stage loads, mutates and saves the same file. Two explorers saving at once overwrite each other.

Each explorer writes only its own file. The context builder is the only stage that combines them.

Reviews merge into the next stage

reviews.mjs applies agent N's review when stage N+1 runs. With four explorers there's no single next stage.

Each explorer applies its own agent's review into its output file before the context builder reads it.

Handoffs are a chain

agents.mjs passes every earlier agent's findings forward, and the token budget is checked between agents.

Explorers get only the scope handoff. The context builder gets all four. Check the budget before the fan-out and give each explorer its own cap.

Decisions still open

  1. env.yaml. What goes in it? Proposed: UI base URL per environment, a login method (saved browser session or user and password from .env), and the Playwright options. Secrets stay in .env.
  2. Baseline. Does it mean "only stories changed since the last run", or "the last run's results to diff against"?
  3. UI safety. Read-only exploration (navigate, open dialogs, trigger client-side validation, never save, submit or delete) or full actions on a dedicated test env? Read-only is safer and should be enforced in the tool allowlist, not only in the prompt.
  4. UI token cost. A browser snapshot costs roughly 5–20k tokens per page. Should UI exploration run on every run or behind an opt-in flag with its own budget?
  5. Context builder. Is it a script plus one LLM call, as proposed, or an agent that can also reason over the joined context?

Rules a change must keep

  • Zephyr has no delete endpoint. Cases are created only through create-approved (dry run, then --yes) after explicit approval.
  • No Jira comments or issue changes during an analysis.
  • Agents change state only through their own review file, never state.json or the workbook.
  • The UI explorer must not change data in the app unless the target environment is explicitly a disposable test env.
  • Report tokens only, never cost; a test enforces it. Every decision row carries a reasoning string.
